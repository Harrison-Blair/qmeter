# V1 — phase 1 report

## Result

Reproduced the unresponsive dashboard in a Herdr pane with real providers. The
user's `~/go/bin/qmeter` is the same source revision: `go version -m` reports
`vcs.revision 978f2ba48f14`.

I set `refresh_interval = 1` in a scratch
`XDG_CONFIG_HOME/.../qmeter/config.toml`, used a separate scratch
`XDG_CACHE_HOME`, and left `QMETER_NO_UPDATE_CHECK` unset. The dashboard fetched
real data from four providers. About three seconds after launch, the screen
showed the first fetched frame and `refreshing · q quit`. I sent `q` with
`herdr pane send-keys`. Two seconds later the process was still alive and the
screen had not changed. The spinner stayed on the same frame.

I built the checked-out `978f2ba` source with `GOTRACEBACK=all` at run time and
repeated the run. During the run, `r` started a refresh, but `q` and `ctrl+c`
did not exit the process. The screen later updated, so this run showed an
intermittent block rather than a confirmed permanent deadlock. I then sent
`SIGQUIT` while the render path was blocked and captured the full goroutine
dump. I closed the scratch pane after the run.

## Cause and proof

The main goroutine was blocked while Bubble Tea rendered the dashboard. The
stack passed through terminal background-colour detection:

```text
goroutine 1 [syscall]:
  github.com/muesli/termenv.(*Output).waitForData
      termenv_unix.go:131
  github.com/muesli/termenv.(*Output).readNextByte
      termenv_unix.go:150
  github.com/muesli/termenv.(*Output).readNextResponse
      termenv_unix.go:172
  github.com/muesli/termenv.Output.termStatusReport
      termenv_unix.go:275
  github.com/muesli/termenv.Output.backgroundColor
      termenv_unix.go:103
  github.com/charmbracelet/lipgloss.(*Renderer).HasDarkBackground
      lipgloss/renderer.go:146
  github.com/charmbracelet/lipgloss.AdaptiveColor.color
      lipgloss/color.go:100
  github.com/Harrison-Blair/qmeter/internal/display.ResetRows
      internal/display/resetlist.go:99
  github.com/Harrison-Blair/qmeter/internal/dash/layout.measurePanels
      internal/dash/layout/screen.go:223
  github.com/Harrison-Blair/qmeter/internal/dash/layout.Screen
      internal/dash/layout/screen.go:85
  github.com/Harrison-Blair/qmeter/internal/dash.Model.View
      internal/dash/model.go:220
  github.com/charmbracelet/bubbletea.(*Program).eventLoop
      bubbletea/tea.go:502
```

`layout.Screen` creates a new `display.Renderer(os.Stdout)` on each call at
`internal/dash/layout/screen.go:64`. Rendering an adaptive provider colour
then calls Lipgloss `HasDarkBackground`. `termenv` sends terminal status
queries and reads the response from the terminal; its Unix wait is five
seconds (`termenv_unix.go:18, 125-156`). Bubble Tea also reads this terminal
for key input. Since the renderer is new on each view, Lipgloss's per-renderer
`sync.Once` does not prevent the next view from querying again. This blocks
Bubble Tea's event loop during `View` for up to five seconds and lets the
status query compete with Bubble Tea for terminal input. Since each subsequent
view makes a new renderer, the query can repeat. This accounts for frozen
frames and missed keys.

The passive update hint is called only after `Run` returns
(`cmd/dash/dash.go:97-106`), so it does not run beside the dashboard and is not
the cause. The dashboard code has no `tea.Exec` or second `tea.Program`; fetch,
spinner, and refresh work run as Bubble Tea commands.

## Proposed fix

Prevent terminal background-colour probing from `View`. Set an explicit
background value on the dashboard renderer before it renders, and reuse that
renderer for dashboard frames. Keep it bound to the destination output. Select
the background value without reading terminal input while Bubble Tea runs.

## Limits

This report covers the first fetch, one automatic refresh, a manual refresh,
`q`, and `ctrl+c`. The captured block returned during the longer debug run, so
I did not prove that one block lasts indefinitely. I did not run the
longer-duration, resize, or deliberately slow/offline-provider cases before
reporting the stack-proven cause. I made no Go source changes. Phase 2 needed
the manager's approval at the time of this report.

## Phase 2 follow-up

The skipped resize and slow-provider cases were run after the approved fix.
During a live refresh, the Herdr pane changed from 26 to 29 rows, then changed
size again. The dashboard stayed responsive; `r` started a refresh and `q`
exited in 59 ms. In a separate run, a local proxy delayed the real Claude
provider's HTTPS `CONNECT` by four seconds and returned 502. `q` exited while
the fetch waited in 64 ms. The shell was restored in both runs. See
[V3.md](V3.md) for the full live-run record.
